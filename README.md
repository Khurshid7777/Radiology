# CardioLens — система детекции и интерпретации ЭКГ

Production-grade система интерпретации ЭКГ по [ТЗ](docs/TZ_ECG_CardioLens.md):
6-слойная архитектура с причинно-следственным анализом, LLM-нарративом на
русском и узбекском, двумя режимами работы и полной трассируемостью
(«regulator-ready»).

> **Дисклеймер.** Инструмент поддержки принятия решений. **Не заменяет врача.**
> Не является медицинским изделием; клинически не валидирован.

## Что реализовано (рабочий MVP-срез)

Сквозной конвейер на цифровом входе с **реальными алгоритмами** в каждом слое
(не заглушки), осмысленным подмножеством находок и всеми пятью форматами вывода:

| Слой | Модуль | Содержание |
|------|--------|-----------|
| 1. Приём | `layer1_ingestion` | Парсеры **WFDB, EDF/EDF+, CSV, DICOM waveform ECG, SCP-ECG** (D94, D95) → единое представление (мкВ, канонические имена отведений); **оцифровка 12-канальной страницы 3×4 + ритм-полоса** с деcкью и устойчивостью к порче фото (`digitize.py`); синтетический генератор (в т.ч. трепетание, АВ-блокада, БНПГ); хук PTB-XL. MUSE/Philips — интерфейсы с `TODO`; приём DICOM от аппарата по сети — `cardiolens.dicom_listener` (D96); **проверка записи перед измерением** — NaN, частота, длительность, единицы, согласованность заголовков; неизмеримая запись отклоняется с причиной (D97) |
| 2. Предобработка | `layer2_preprocess` | Ресемплинг, режектор 50/60 Гц, полосовой без искажения ST; per-lead SQI, lead-off; **детекция реверса LA/RA** |
| 3. Измерения | `layer3_measure` | QRS (neurokit2 + многоканальная огибающая), P по амплитуде, **конец T касательной по всем отведениям**, PR/QRS/QT, **QTc Fridericia/Bazett/Framingham**, ЧСС/HRV, ось QRS, ST в J/J+60/J+80 от PR-сегмента, вольтаж, **предсердная активность независимо от QRS** (F-волны по спектру, диссоциированные P) |
| 4. Находки | `layer4_findings` | Ритм (синус, бради/тахи, **ФП, трепетание, полная АВ-блокада**), проводимость (**БПНПГ/БЛНПГ, WPW**, АВ-блокада I), интервалы/QT, ишемия (**ST по территориям + реципрокные; перикардит vs STEMI**, нейтральный `st_elevation_any`, вторичные ST-T при БНПГ/ГЛЖ), ГЛЖ, **отклонения оси, низкий вольтаж, увеличение предсердий** — с evidence и confidence; **обучаемый слой** (`ml.py`, sklearn) добавляет `ml_p` как свидетельство и `ml_suggested_*` |
| §10 Safety | `safety` | Критические «нельзя пропустить»: STEMI, длинный QT, паттерн гиперкалиемии, тяжёлая брадикардия, широкие тахикардии — независимо от LLM/режима |
| 5. Каузальный | `layer5_causal` | networkx-граф над YAML-правилами: цепочки причина→следствие, метки физиологично/патологично, флаги неправдоподобности |
| §8.4 Серийное | `serial` | Сравнение с прошлой ЭКГ: новые/разрешившиеся находки, QTc/ЧСС-динамика; новая элевация ST → критично + эскалация |
| 6. Интерпретация | `layer6_interpret` | `LLMProvider`: **Claude**, **локальная OpenAI-совместимая LLM** (Ollama/llama.cpp/vLLM), offline-**Stub**; заземление (drop незаземлённых утверждений); политика режимов A/B/эскалация; RU/UZ |
| §11 Выходы | `outputs` | JSON, заключение RU/UZ, SVG-разметка кривой, каузальный граф, PDF |
| §4 Поток | `streaming` | Скользящие перекрывающиеся окна (10 с, шаг 5 с) с онлайн-обработкой; ловит момент появления критической находки |
| §14 API/UI | `api` | FastAPI-сервис + одностраничный веб-интерфейс: загрузка/выбор → анализ → все 5 форматов |

Конфигурация без хардкода: `configs/app.yaml` (режим, пороги, частота сети),
`configs/norms/{adult,pediatric}.yaml` (возрастные нормы),
`configs/rules/pathophysiology.yaml` (база каузальных правил).

## Установка

```bash
python3.11 -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"        # ядро + pytest
pip install -e ".[dev,llm]"    # + Claude-провайдер (anthropic)
```

## Запуск демо (сквозной пример, ТЗ §18)

```bash
python -m cardiolens.demo --case normal        # синтетическая норма
python -m cardiolens.demo --case hyperk --mode B   # гиперкалиемия → эскалация
python -m cardiolens.demo --case stemi         # инфаркт → критический алерт
python -m cardiolens.demo --case child         # педиатрические нормы
python -m cardiolens.demo --wfdb <record>      # реальная запись WFDB/PTB-XL
python -m cardiolens.demo --stream             # потоковый режим: STEMI на 20-й сек
```

Все пять форматов вывода пишутся в `outputs/`.

Для офлайн-детерминизма используйте синтетический генератор (по умолчанию).

### LLM-нарратив через Claude (ТЗ §9, §12)

По умолчанию работает offline-`StubProvider`. Для нарратива через Claude:

```bash
export ANTHROPIC_API_KEY=...      # ядро (Слои 1–5) остаётся офлайн
pip install -e ".[llm]"
```

`ClaudeProvider` подключается автоматически, если ключ и пакет доступны;
заземление проверяется в любом случае.

### Полностью офлайн: локальная LLM (ТЗ §12, §17)

Слой 6 умеет работать с любым OpenAI-совместимым сервером — Ollama, llama.cpp,
vLLM, LM Studio. Тот же промпт, те же токены заземления, тот же валидатор.

```bash
ollama serve && ollama pull llama3.1:8b          # http://127.0.0.1:11434/v1
# configs/app.yaml -> llm.provider: "local" (или "auto": Claude → локальный → stub)
python -m cardiolens.demo --case normal
```

Если сервер недоступен или вернул мусор, отчёт всё равно будет — на
детерминированной заглушке, с пометкой в трассе рассуждений. Ключ Claude не
нужен; наружу не уходит ничего. Кто написал нарратив, видно в JSON
(`interpretation.provider` = `local` / `claude` / `stub`, `provider_model`),
в трассе рассуждений и в шапке веб-интерфейса.

Переменные окружения перекрывают блок `llm` в `configs/app.yaml` без правки
репозитория: `CARDIOLENS_LLM_PROVIDER`, `CARDIOLENS_LLM_BASE_URL`,
`CARDIOLENS_LLM_MODEL`, `CARDIOLENS_LLM_TIMEOUT_S`.

### Локальная LLM + веб-интерфейс одной командой

```bash
scripts/run_local.sh                    # venv → ollama serve → ollama pull → http://127.0.0.1:8000
scripts/run_local.sh --no-llm           # только веб-интерфейс, нарратив — заглушка
CARDIOLENS_LLM_MODEL=qwen2.5:7b scripts/run_local.sh
```

Скрипт ставит пакет в `.venv`, поднимает Ollama (если установлена; иначе
печатает, как установить, и запускает сервис на заглушке), один раз скачивает
модель и стартует `uvicorn`. Через Docker — то же самое без установки чего-либо,
кроме Docker:

```bash
docker compose up                       # ollama + cardiolens → http://localhost:8000
```

`docker-compose.yml` поднимает контейнер Ollama (веса — в томе `ollama`),
одноразово скачивает модель и запускает сервис, указав ему
`CARDIOLENS_LLM_BASE_URL=http://ollama:11434/v1`. Первый запуск скачивает
≈ 5 ГБ весов; дальше всё офлайн. Проверка: `curl localhost:8000/health` → поле
`llm.active` должно быть `local`.

### Оцифровка бумажной ЭКГ: страница 3×4 (ТЗ §4, §17)

```python
from cardiolens.layer1_ingestion import digitize_page_to_signal, render_ecg_page, degrade_image
sig = digitize_page_to_signal("photo.jpg", px_per_mm=6, mm_per_s=25, mm_per_mv=10)
result = run_pipeline(sig, mode="A")   # sig.provenance.lead_windows — где у отведения есть данные
```

Деcкью по линиям сетки (Hough), порог по отношению к локальной яркости (тень и
сетка не мешают), фильтр связных компонентов (JPEG-звон, соль, подписи
отведений), базовые линии строк из проекции чернил, панели — из геометрии
раскладки. Слой 3 учитывает окна отведений: ось, вольтаж, ST и QT считаются
только по комплексам внутри окна. `render_ecg_page` + `degrade_image` дают
воспроизводимый бенчмарк:

Калибровка теперь читается с изображения (D43): px/mm — из периодичности сетки и
шага строк раскладки, mm/mV — из калибровочного импульса 1 мВ (`render_ecg_page(...,
calibration_pulse=True)`); перспектива фото снимается по точкам схода линий сетки.
Результаты без заданной калибровки (`px_per_mm=None, mm_per_mv=None`), 3 seed:

| чистый скан, поворот 3°, JPEG 40, тень 50 %, соль 0.5 % | 0.93 | 0.96 | < 1 % |

| фото с виньеткой и зерном при ≥ 3.5 % | 0.1–0.6 | — | — |

Первый прогон показал: ритм и частота со страницы надёжны, набор находок — нет
(совпадал у 18 % чистых страниц), потому что оцифрованный QRS был шире на +24 мс
(медиана): штрих 3–4 px размазывает крутой фронт на соседние столбцы, а глубокие
S соседней строки попадали в медиану панели. D47 заменил медиану столбца
трекингом своей трассы (скелет + Витерби по сериям чернил, расширенная панель,
вершина из сырых чернил): QRS MAE 25 → 12 мс, r 0.90 → 0.94, совпадение наборов
0.57 → 0.69, полностью совпали 31 % страниц; на сканах 0.48 → 0.60. Фото 2 % почти
не сдвинулось — там предел в снятии перспективы, а не в извлечении. Остаток
смещения (+8 мс медиана на 15 контрольных записях) — склоны у вершины, читаемые по
середине сырой серии; подробности и отвергнутые варианты — в CLINICAL_REFERENCES.

D52 разобрал оставшиеся расхождения — они оказались амплитудными и
измерительными, а не трекинга как такового: соседние столбцы-вершины гасили друг
друга (R 26 px читался как 17), гейт P/T-пересчёта сравнивал удары столбца
страницы с грудными отведениями (целый столбец ударов терялся → ложная ФП),
«вольтаж конечностей» был вольтажом одного II, а один пропущенный удар давал ФП.
На тех же 100 чистых страницах: наборы находок совпали **36 → 51 %**, смещение QRS
медиана **+8 → +4 мс**, ложный «низкий вольтаж» **19 → 5** страниц, отношение
амплитуд страница/запись 0.83 → 0.91 (при 12 px/mm, т.е. ≈ 300 dpi, — 0.94 и
r 0.97: остаток — разрешение рендера, не извлечение).

D55 и D57 закрыли ритмическую часть расхождений. Удары на странице теперь
находятся по всем отведениям столбца (огибающая по четырём действительным
отведениям, нормированная внутри столбца), список сливается с одно-канальным:
подтверждённый удар остаётся на месте, неподтверждённый (P/T) уходит, пропущенный
добавляется при сильной огибающей, удар на границе столбца судится по ритм-полосе,
и каждая правка должна укладываться в ритм подтверждённых ударов (добавленному
нужно место, выброс не может открыть разрыв — иначе на фотографиях столбцы
добавляли шум внутрь нормальных RR). На 100 страницах: чистые — ЧСС ±3 уд/мин
**88 → 94 %**, ложная ФП **5 → 2**, потеря синусового ритма 5 → 2, наборы совпали
51 → 52 %; скан 88 → 94 %; фото 2 % **52 → 60 %**; фото 3.5 % 35 → 38 %; две
оставшиеся ФП стоят на границе гейта уже в цифровой записи. D57 — отрицательный результат: ужесточение
привязки сторон четырёхугольника к линиям сетки (D48) выигрывало на 24 сеяных
случаях с поворотом и виньеткой, но на 100 страницах проиграло (фото 2 % r
0.654 → 0.60, ЧСС ±3 уд/мин 48 → 39 %; перспектива 5 % 0.844 → 0.826) ради
выигрыша только на повёрнутых виньетированных страницах 3.5 % (0.39 → 0.43),
где лучше всего вообще не привязывать (0.48). Ограничения откачены, свип семи
конфигураций — в CLINICAL_REFERENCES. Полная «фотография» 3.5 % (виньетка +
зерно + соль + JPEG 40) нечитаема при любой привязке к краям: разрушена сама
текстура сетки.

D64 сменил сам принцип снятия перспективы: не края страницы (Хаф по Canny —
абляция показала, что он ломается на трассе, тени и зерне: без размытия r хуже,
0.42), а **текстура сетки** — локальная частота сетки по плиткам 160 px из 2‑D
спектра и одна гомография, подогнанная ко всем плиткам; аффинные случаи (скан,
поворот) оставлены деcкью. На 100 страницах r трассы: фото 2 % **0.65 → 0.81**
(страниц < 0.5: 34 → 13), перспектива 3.5 % с виньеткой и поворотом **0.39 → 0.84**
(68 → 9), чистая перспектива 2 / 5 % 0.81 / 0.84 → 0.91 / 0.91, полное фото 3.5 %
0.23 → 0.52, скан без изменений.

### Лента 12×1 с телефона (ТЗ §4, §17, D72)

Прикроватные аппараты печатают «12L»: двенадцать строк в одну колонку, метки
слева, импульс 1 мВ перед каждой третьей строкой. `digitize_auto_to_signal`
считает строки по чернилам и выбирает между страницей 3×4 и лентой 12×1;
`digitize_strip_to_signal` читает ленту: цветная маска чернил (нейтральные
тёмные пиксели, без красной сетки и синей ручки), деформация маски тем же
отображением, что и фото (`apply_dewarp`), базовые линии строк как решётка
известного шага по плиткам, выпрямление каждой строки и трекер страницы,
снятие «мостов» на соседнюю строку и пересечений с сеткой, импульсы → мм/мВ.

```python
from cardiolens.layer1_ingestion import digitize_auto_to_signal, render_ecg_strip
sig = digitize_auto_to_signal("strip_photo.jpg")      # 3x4 page or 12x1 strip, from the ink
```

Синтетика (`render_ecg_strip`): чистая лента 6 px/мм — r 0,93 по отведениям,
JPEG q75 — 0,93, «фото» (перспектива, поворот, размытие, тень, виньетка) —
0,90; при 4 px/мм 0,83 / 0,78. Первое реальное фото ленты (960×1280, 3,9 px/мм —
столько оставляет сжатие Telegram): строки и масштаб прочитаны, морфология
большинства отведений совпадает с наложением на снимок, ритм ненадёжен
(детектор ударов на разрывах трассы в 1 px). Для реальной работы ЭКГ нужно
присылать **файлом** (без сжатия, ≈ 12 px/мм с телефона), см. DECISIONS D72.

### Обучаемый слой поверх правил (ТЗ §17)

`cardiolens.ml`: признаки v2 — 79 сводных признаков Слоя 3 + 300 признаков формы
среднего комплекса по отведениям (D46) → per-class HistGradientBoosting (sklearn);
набор признаков версионируется, артефакт другой версии отвергается.
Модель — **свидетельство, не авторитет** (D33): вероятность попадает в evidence
находки (`ml_p`), согласие поднимает уверенность, несогласие только фиксируется,
`ml_suggested_<код>` — лишь для классов, где модель точна (spec ≥ 0.95) на всех
наборах и не хуже правил на каждом чужом наборе в обе стороны переноса (≥ 20
позитивов); сейчас таких классов **нет**. Safety-слой ML не видит.

```bash
python -m cardiolens.ml.train --train data/ecg-arrhythmia-train data/ecg-arrhythmia data/ptbxl \
```

## Веб-приложение (FastAPI + UI)

## Подключение электрокардиографа (D94–D96)

Цифровая запись точнее любого фото. Три пути, от простого к сложному.

1. **Файл.** Экспорт из аппарата или его программы загружается в `/api/analyze` или через форму
   веб-приложения:
   - форматы: DICOM waveform ECG (`.dcm`), SCP-ECG (`.scp`), WFDB, EDF, CSV;
   - DICOM и SCP распознаются и без расширения — по метке `DICM` и по CRC с меткой `SCPECG`.
2. **Отправка по сети (DICOM).** Если аппарат умеет «отправить на сервер / PACS»:

   ```bash
   pip install -e ".[dicom]"
   # configs/dicom_listener.yaml: allowed_calling_aes: ["<AE title аппарата>"], host/port
   uvicorn cardiolens.api.app:app --port 8000 &
   python -m cardiolens.dicom_listener
   ```

   На аппарате указываются IP сервера, порт (11112) и AE title `CARDIOLENS`.
   - Каждая принятая ЭКГ уходит в `/api/analyze`.
   - Аппарат получает «успех» или отказ с причиной.
   - Журнал пишется в `data/dicom_inbox/received.jsonl`: время, AE аппарата, хеш UID, id анализа; без
     данных пациента.
   - Без белого списка AE приёмник не запускается. Оригиналы на диск не пишутся.
3. **Свой протокол аппарата (Wi-Fi / Bluetooth).** Только по SDK или документации производителя.

**Не проверено на настоящих файлах аппаратов.** Отказ, а не догадка: SCP-ECG с вычитанием опорного
комплекса, с бимодальным сжатием или с собственными таблицами Хаффмана; DICOM без чувствительности
канала.

(176 записей с P), QRS 9.8 мс, QT 15.6 мс**. По диагнозам заголовков: ФП 11/15 при
spec 0.995, БЛНПГ 4/4, БПНПГ 3/4, АВ-блокада I 6/10; «ГЛЖ» у 108 из 200 и «ось
влево» у 66 (медиана измеренной оси −2°, лишь 12 % ниже −30°) — собственные
определения LUDB, отражены как семантика меток; 8 записей «STEMI: стенка» алерт не
ловит (0/8) — открытое наблюдение рядом с PTBDB.

**Анализ ошибок по ярусам риска и протокол валидации (блокер 1 обзора применения).**
`configs/risk_tiers.yaml` делит коды находок на critical (ТЗ §10) / major / minor;
харнесс считает пропуски и ложные вызовы по ярусам на уровне меток и на уровне
случая (случай с критической меткой «пойман», если выдана любая критическая
находка — так эскалирует режим B); коды, которых набор не размечает, выводятся
как частота вызова, а не как ошибка. Проспективный протокол (STARD, две стадии,
конечные точки, размер выборки, планки приёмки по ярусам) — `docs/VALIDATION_PROTOCOL.md`.
Первый же прогон вскрыл две причины ложных критических тревог (35 % случаев на 664):
**длинный QT при широком QRS** (D60: QT − 0.485·QRS по Богоссяну при QRS ≥ 120 мс
или блокаде; ложных 91 → 43 на 664, 174 → 80 на PTB‑XL при неизменной
чувствительности на PTB‑XL) и **«остроконечные T», ловившие хвост QRS** (D61: окно T
после QRS и до следующего удара, описатель формы по медианному комплексу —
полуширина и асимметрия, критерий «высокий И узкий И симметричный» в таблице норм;
вызовы 21 % → 0.9 % на 664, 14 % → 0.4 % на PTB‑XL). Ложные критические тревоги на
уровне случая: 664 35 % → 8.9 %, PTB‑XL 8.5 %, PTBDB 4 %, CPSC 1 %, LUDB 0 %, дети 2.3 %;
критическая чувствительность 0.23–0.55 — далеко от планки 0.90, и причина не в
порогах, а в метках (см. блокер 2). Таблица по наборам — в CLINICAL_REFERENCES.

**MIMIC‑IV‑ECG — явные ЭКГ‑метки STEMI, высоких T и длинного QT (D62; блокер 2).**
Три эксперимента по чувствительности STEMI на PTBDB отрицательные и записаны
(суммарная элевация по территории, серийный критерий по псевдо‑базе, обучаемый
«второй голос» с AUC 0.94 на обучении и 0.59 на PTBDB): промахи PTBDB — состав
набора («инфаркт ≤ 1 дня» включает NSTEMI), а не подпороговая элевация. Нужна
явная метка — и она нашлась: MIMIC‑IV‑ECG (800 035 ЭКГ, Open Access) с
заключениями электрокардиографа; `fetch_mimic` берёт по 300 записей на класс

0.76 / 0.94, ФП 0.58 / 0.95; критерий остроконечных T ловит 14 из 307 «TALL T

набора (~45k) — перед клиническими выводами прогнать на большей выборке.

## Обратная связь и калибровка (§13)

- **Захват правок врача:** `POST /api/analysis/{id}/feedback` — по каждой
  находке `confirmed | corrected | rejected` пишется в append-only JSONL
  (`cardiolens.feedback`). Топливо для дообучения и калибровки.
- **Калибровка уверенности:** temperature scaling (`cardiolens.calibration`);
  `POST /api/calibration/fit` обучает T на накопленных подтверждениях/отклонениях
  и считает ECE (до/после). До накопления меток — тождество (T=1, no-op).
  Пайплайн применяет калиброванную уверенность к находкам.

## Telegram-агент: сбор фото ЭКГ из групп и проверка врачом (§13, §15)

`cardiolens.telegram` слушает выбранные группы через **ваш собственный аккаунт**
(Telethon), ничего в группы не пишет, каждое фото с миллиметровой сеткой
прогоняет через оцифровщик и пайплайн и присылает карточку в «Избранное»
(Saved Messages): фото, что прочитал оцифровщик, ЧСС/PR/QRS/QTc/ось, находки,
критические алерты, коды. Ваш ответ на карточку становится меткой:

| Ответ | Смысл |
|-------|-------|
| `+` | все находки верны |
| `-` | ни одна находка не верна |
| `-st_elevation +lbbb` | убрать / добавить коды (список кодов: `/help`) |
| любой текст | комментарий без метки |
| `/stats` | счётчики: собрано, ждёт проверки, вердикты |

```bash
pip install -e ".[telegram]"
export TELEGRAM_API_ID=... TELEGRAM_API_HASH=...      # https://my.telegram.org
python -m cardiolens.telegram chats          # первый запуск спросит телефон и код; выведет ваши группы с id
# configs/telegram.yaml -> groups: ["@ecg_group", -1001234567890]   (из списка выше)
python -m cardiolens.telegram run            # слушать группы, слать карточки в «Избранное»
python -m cardiolens.telegram backfill       # один проход по истории групп (backfill_limit)
python -m cardiolens.telegram stats          # офлайн: счётчики и согласие с проверкой
python -m cardiolens.telegram export         # офлайн: харнесс на проверенных фото
python -m cardiolens.validate --telegram data/telegram
python -m cardiolens.telegram analyse photo.jpg   # одно фото тем же путём, без Telegram
```

Что накапливается в `data/telegram/` (git-ignored): фото без EXIF, оцифрованный
сигнал (`.npz`), `dataset.jsonl` с предсказанием и вердиктом, картинка для
проверки. Отправитель хранится только как хэш. Вердикты пишутся и в
`data/feedback/feedback.jsonl`, так что `POST /api/calibration/fit` калибрует
уверенность на реальных проверках. Проверенные записи — первый бенчмарк
оцифровщика и правил на **настоящих фотографиях** (`--telegram` в харнессе даёт
те же метрики и ярусы риска, что и для PhysioNet). Нарратив в карточках —
заглушка (`narrative: false`); с `true` берётся провайдер из `configs/app.yaml`
(локальная LLM / Claude). Ограничения: Telegram не поощряет автоматизацию
аккаунтов — агент только читает и пишет вам в «Избранное», рассылок нет;
фото плохого качества оцифровщик может не прочитать — такие случаи всё равно
попадают в набор с пометкой и вашей меткой. Telegram сжимает фото до 1280 px по длинной
стороне (≈ 4 px/мм для ленты) — просите присылать ЭКГ **файлом** («без сжатия»):
агент читает и фото, и документы, а оцифровщик измерен на 6–12 px/мм (D72).

## Дорожная карта (ТЗ §17, v2)

Сделано из v2: оцифровка страницы с порчей фото, обучаемый слой поверх правил,
локальная LLM (полный офлайн), потоковый режим, серийное сравнение, возрастная
страта оценки. Не сделано и почему — в [TZ_COVERAGE](docs/TZ_COVERAGE.md):
реальные фотографии и калибровочный импульс, DL на сырых отведениях,
педиатрический fine-tuning (нет размеченного детского набора), расширение
автономного режима, путь к сертификации.
