## 2. Стек и структура

- Python ≥ 3.11, один дистрибутив `cardiolens`, src-layout (`src/cardiolens`), setuptools.
- Зависимости: numpy, scipy, pydantic 2, pyyaml, networkx, wfdb, pyedflib, neurokit2,
  matplotlib, reportlab, fastapi, uvicorn, python-multipart. OpenCV
  (`opencv-python-headless`) стоит только в extras `digitize`/`telegram`/`dev`.
- Конфигурация: `configs/app.yaml` (+ переопределения через `CARDIOLENS_*` env),
  `configs/norms/*`, `configs/rules/*`, `configs/telegram.yaml`. Пороги в коде
  оформлены как именованные модульные константы (например `STRIP_*` в `strip.py`).
  **В YAML они не вынесены**, а ТЗ сканера (§0.3) этого требует.
- Документация решений: корневой `DECISIONS.md` (D1–D91, по-русски, с числами
  измерений). Покрытие ТЗ: `docs/TZ_COVERAGE.md`.
- Развёртывание: `Dockerfile`, `docker-compose.yml` (Ollama + сервис),
  `scripts/run_local.sh`.
- Flutter, Dart и мобильного кода в репозитории **нет**. Flutter SDK в среде
  разработки тоже нет (`which flutter` → пусто).

## 3. Контракт сигнала Cardiolens (то, к чему приводит адаптер)

`src/cardiolens/contracts/signal.py` → `SignalRepresentation` (pydantic):

| Поле | Тип / единицы | Замечание для сканера |
|---|---|---|
| `signal` | `float32[n_leads, n_samples]`, **мкВ** | ТЗ сканера: мВ → адаптер умножает на 1000 |
| `sampling_rate_hz` | float | у текущего оцифровщика = px/мм × мм/с (например 150 Гц), Слой 2 потом ресемплирует до 500 Гц (`configs/app.yaml`) |
| `lead_names` | канонические `I…V6` (`canonical_lead_name`) | совпадает с ТЗ |
| `duration_s` | float | |
| `source` | строка: `wfdb\|edf\|…\|image\|stream\|csv\|synthetic` (Telegram пишет `telegram-photo`) | для сканера: `image` |
| `patient`, `context` | возраст, пол, K⁺, Ca²⁺… | сканер не заполняет. Шапку не читаем (приватность) |
| `quality.per_lead_sqi`, `quality.flags` | | Слой 2 перезаписывает своим SQI |
| `provenance.digitized` | bool | эквивалент `digitized_from_image` |
| `provenance.confidence` | 0..1 \| None | сейчас = средняя доля столбцов с найденной трассой |
| `provenance.lead_windows` | `{lead: (t0_s, t1_s)}` | **вне окна сэмплы = 0, а не NaN**. Слой 3 (`measure.py:251,462,528`) меряет только внутри окна |
| `provenance.notes` | list[str] | калибровка пишется строкой `"calibration: {...}"` |

Ключевые факты:

1. **`provenance.digitized` нигде ниже Слоя 1 не читается.** Уверенность отчёта,
   гейт автономного режима B (`pipeline.py` → `interpret(..., quality_ok=...)`),
   заключение RU/UZ и PDF о происхождении «с фото» не знают. Фото может дать
   автономный отчёт в режиме B, и пометки «получено по фото» в отчёте нет. Требование
   ТЗ §7/§12 сейчас не выполняется (это работа M4).
2. Пропуски трассы **молча интерполируются** (`digitize._fill_gaps` → `np.interp`).
   Это противоречит ТЗ §7 («пропуски помечаются явно, не интерполируются молча»).
3. Внутри окна отведения нет маски пропусков: контракт умеет «отведение есть в
   [t0, t1)», но не умеет «внутри окна 80 мс потеряно».

Встречный контракт — JSON-выход `outputs/json_out.py` (результат анализа, а не вход),
сканер его не меняет.

## 4. Что уже есть по «фото/скан» (вход модальности)

Оцифровка в CardioLens существенно продвинута: решения D21, D35, D43, D47, D48,
D52, D55, D57, D64, D72. ТЗ сканера написано как будто с нуля. На деле значительная
часть M2/M3 уже реализована и измерена.

| Возможность | Где | Состояние (числа из DECISIONS/README) |
|---|---|---|
| Одноканальная чистая полоса | `digitize.digitize_image` | медиана по столбцу. `load()` для .png/.jpg идёт сюда, то есть многоканальная страница через `load()` читается **неправильно** |
| Страница 3×4 + ритм II | `digitize.digitize_page` → `page_to_signal` | r 0.93–0.96 на скан-порче, QRS +4 мс (D52/D55, 100 страниц PTB-XL) |
| Лента 12×1 | `strip.digitize_strip` | синтетика r 0.93 при 6 px/мм, 0.83 при 4. Одно реальное фото (D72): строки и масштаб прочитаны, ритм нет |
| Авто-выбор раскладки | `strip.count_rows` + `digitize_auto_to_signal` | только 3×4 ↔ 12×1 по числу строк. **6×2 нет**, реестра форматов нет |
| Выпрямление перспективы | `dewarp_page`: текстура сетки (D64) → четырёхугольник (D48) → точки схода (D43) → аффинная поправка | фото 2 %: r 0.81, 3.5 % + виньетка 0.84, «полное фото 3.5 %» 0.52 |
| px/мм | `estimate_grid_pitch(_xy)` (автокорреляция по плиткам) + шаг строк раскладки | ошибка масштаба < 1 % (скан), 2–3 % (фото) |
| Усиление | `detect_calibration_pulse` / `strip._find_pulse` | высота импульса → мм/мВ, ошибка < 3 %. Если импульс не найден, **молча 10 мм/мВ** |
| Скорость бумаги | — | **не определяется**: параметр `mm_per_s=25.0` по умолчанию. 50 мм/с нигде не тестировался |
| Сегментация трассы | порог к локальному среднему, цветовая маска (`ink_mask_colour`), фильтр компонент, стирание текста (`_erase_text_lines`), закраска ручки | классика без интерфейса `Segmenter` |
| Векторизация | `_trace_rows_tracked`: скелет Zhang–Suen + Витерби по сериям чернил + вершина из профиля штриха (D47/D52) | это и есть «путь по тёмным пикселям (DP)» из ТЗ §5.7. «Взвешенного центроида» нет, медиана столбца есть (`tracked=False`) |
| Уверенность | `provenance.confidence` = покрытие столбцов | по отведениям нет. Кодов отказа нет. Проверки Эйнтховена/Гольдбергера нет |
| Генератор синтетики | `render_ecg_page`, `render_ecg_strip`, `degrade_image` (поворот, размытие, JPEG, тень, соль, перспектива, виньетка, текстура) | своя замена ECG-Image-Kit, детерминированная по seed |
| Бенчмарк «фото + запись» | `validation/ecg_images.py`, `python -m cardiolens.validate --ecg-images <dir>` | макет ECG-Image-Database/Challenge-2024. Сами данные недоступны (404) |
| Тесты оцифровки | `test_digitize*.py`, `test_strip_digitizer.py`, `test_grid_texture_dewarp.py`, `test_oversense_page.py`, `test_ecg_images_adapter.py`, `test_telegram_agent.py` | 51 тест |

Метрики сквозного пайплайна на 100 страницах PTB-XL (D64), чтобы сравнить с
целью ТЗ «≤ 10 мс»: на фото с 2 % перспективы **QRS MAE 27.4 мс**, ЧСС ±3 уд/мин у 70 %;
на чистых страницах смещение QRS +4 мс.

## 5. API и клиенты

- **FastAPI** `src/cardiolens/api/app.py`: `POST /api/analyze` (синтетика или
  WFDB/EDF/CSV), отчёты по `analysis_id`, `POST /api/analysis/{id}/feedback`,
  `POST /api/calibration/fit`. **Изображения API не принимает**
  (`service.signal_from_uploads` → «unsupported upload»). Аутентификации нет.
  Хранилище: in-memory LRU на 200 записей. Очереди задач нет, всё синхронно.
  Лимит загрузки 64 МБ.
- **Telegram** `src/cardiolens/telegram/`: **это не бот**, а коллектор через
  пользовательский аккаунт (Telethon, D71). Читает группы, в которых состоит
  владелец, оцифровывает фото, шлёт карточку в «Избранное», вердикт `+/-/±код`
  становится меткой и уходит в `FeedbackStore`. Фото **перекодируется без EXIF и
  уменьшается до 2400 px** (`save_photo`), оригинал не хранится.
- **Обратная связь**: `feedback/store.py`, JSONL append-only, обратная связь по
  находкам. Поправок калибровки (скорость/усиление) в модели нет.
- Веб-UI: `api/static/index.html`, одна страница.

## 7. Противоречия ТЗ с репозиторием и средой

1. **«Сначала изучи и ничего не ломай» против «строим модуль».** Оцифровщик уже
   есть и измерен. Переписывать его с нуля значит потерять D35–D72. Предложение
   (SD-003): `ecgscan` начинается как обёртка над существующими алгоритмами (это
   «v0»-базовая линия в бенчмарке M1), затем по этапам выносит их в свои
   модули. Каждая замена принимается, только если не хуже на бенчмарке.
   Публичный API `cardiolens.layer1_ingestion` сохраняется реэкспортом.
2. **Цель «≤ 10 мс для QRS/RR/QT» недостижима в постановке «против эталона».**
   Даже на *цифровом* сигнале делинеатор CardioLens против разметки кардиологов
   LUDB даёт MAE: PR 8.9, QRS 9.8, **QT 15.6 мс**. Оцифровка может только
   добавить ошибку. Предложение (SD-010): критерий 10 мс применять к **ошибке,
   вносимой оцифровкой** (тот же делинеатор на исходном цифровом сигнале против
   оцифрованного с изображения той же записи). Ошибку делинеатора против разметки
   отчитывать отдельно. Сейчас на фото это 27 мс для QRS, так что разрыв большой
   и честный.
3. **Порог 8 px/мм и Telegram.** Telegram сжимает «фото» до 1280 px по длинной
   стороне, на реальном снимке это 3.9 px/мм (D72). При пороге ТЗ все фото из
   Telegram-чата уйдут в `LOW_RESOLUTION`. Значит, бот должен просить отправку
   **файлом (документом)** или загрузку через Mini App. Снимок 12 Мп с листом во
   весь кадр даёт ≈ 12–13 px/мм для A4.
4. **«Сохранить исходник без изменений» против текущей приватности.** Telegram-агент
   намеренно стирает EXIF (GPS) и уменьшает фото. По ТЗ оригинал нужно хранить
   побайтно с хэшем, но зашифрованным, а в рабочих копиях и экспортах удалять EXIF
   (SD-008). Маскирование шапки на устройстве меняет «оригинал» ещё до сервера:
   хэш считается от того, что пришло, а факт маскирования фиксируется флагом.
5. **Скорость по ширине калибровочного импульса.** ТЗ (§5.4) считает это
   «стандартной практикой». Ширина импульса у разных производителей разная (часто
   фиксированная по времени, иногда по мм), универсального правила нет. Генератор
   CardioLens рисует 5 мм при любой скорости. Поэтому ширина импульса — только
   слабое свидетельство с низкой уверенностью. Решающие источники: формат аппарата
   из реестра, OCR шапки и подтверждение врача. Правдоподобность по ЧСС как
   арбитр **не используется**: дети выше 150 уд/мин неотличимы от «50 вместо 25»
   (SD-011).
6. **Telegram: в ТЗ бот с белым списком, в репо коллектор групп через аккаунт.**
   Это разные сценарии. Предложение (SD-009): новый бот (тонкий клиент к
   `POST /scans`), коллектор остаётся как есть. Коллектор при этом источник
   реальных фото для M5, но с оговорками: сжатые ≈ 4 px/мм, без цифрового эталона,
   фото третьих лиц из групп. Вопрос согласия и анонимизации — к заказчику (В4).
7. **Представление пропусков.** ТЗ: NaN или маска. CardioLens: нули вне окна плюс
   интерполяция внутри. Предложение (SD-006): в `ScanResult` пропуск = `null`
   (JSON) / NaN (numpy). Адаптер к `SignalRepresentation` ставит 0 вне окна (как
   сейчас), а внутри окна передаёт маску в новом необязательном поле
   `Provenance.sample_mask`. Изменение контракта аддитивное, Слой 3 учит маску в M4.
8. **Структура папок ТЗ §13** (`cardiolens/scanner/ecgscan/...`) не совпадает с
   src-layout репозитория. Адаптация в §8 ниже.
9. **Данные §11 из среды разработки.** `github.com` и `api.github.com` → 403,
   `codeload` → 403, но `raw.githubusercontent.com` → 200 (отдельные файлы
   доступны). ECG-Image-Database на PhysioNet → 404 (как и в D48). PTB-XL → 200.
   ECG-Image-Kit целиком клонировать отсюда нельзя. Варианты (В5): заказчик
   кладёт архив или разрешает пофайловую загрузку через raw. Либо M1 стартует на
   собственном генераторе, а Kit подключается как необязательный внешний генератор.
10. **Лицензии базовых линий** (проверено по LICENSE на raw.githubusercontent):
    ECG-Image-Kit — **BSD-3-Clause** (использовать можно). Open-ECG-Digitizer
    (Ahus-AIM) — **CC BY-SA 4.0** (ShareAlike): код **не копируем** в репозиторий,
    запускаем только как внешний процесс в бенчмарке (SD-012). ECGtizer и ECGMiner:
    лицензии из среды **не проверены** (403), до проверки не используются.
11. **Flutter.** SDK в среде нет, поэтому собрать и прогнать Flutter-тесты здесь
    нельзя. Для M5 нужен CI-джоб с `subosito/flutter-action` или локальная сборка у
    заказчика. Логику контроля качества кадра предлагается держать в общем
    пороговом конфиге и проверять эталонными векторами, одинаковыми для Python и Dart
    (SD-014).
12. **OCR.** В зависимостях OCR нет. Tesseract требует системный пакет и языковые
    данные (rus/uzb), его нужно добавить в Dockerfile. RapidOCR (ONNX) ставится из
    PyPI. Выбор в M2 по бенчмарку (SD-013). До этого OCR-источник скорости и
    усиления — `TODO` с уверенностью 0.
13. **Режим B.** ТЗ сканера требует подтверждения врачом при неуверенной калибровке
    (§8, §15), но в CardioLens режим B может выдать автономный отчёт. Предложение
    (SD-015): вход с `digitized_from_image` никогда не проходит гейт автономного
    режима, только A или эскалация. Нужно подтверждение (В6).
14. **3×4 на 50 мм/с.** Геометрия страницы в коде выводится из `mm_per_s` (панель =
    2.5 с × скорость). На 50 мм/с реальные аппараты печатают 3×4 по-разному:
    панель 2.5 с на двойной ширине, либо 1.25 с, либо 6×2. Без реальных образцов
    это `TODO` в реестре форматов, низкая уверенность.

## 8. Предлагаемая структура (адаптация ТЗ §13 к src-layout)

```
src/
  ecgscan/                    # чистая библиотека пайплайна, без веба; зависит от numpy/scipy/opencv/pydantic
    __init__.py               # версия пайплайна
    io/                       # приём: байты → оригинал (hash, EXIF, ориентация) + рабочая копия
    capture_qc/               # резкость, блики, наклон, доля листа, px/мм — общие для сервера и эталонов клиента
    geometry/                 # лист, сетка, гомография, px/мм (вынос из cardiolens.digitize по этапам)
    calibration/              # импульс, скорость, усиление, OCR шапки, согласование источников
    segmentation/             # протокол Segmenter: classic, onnx (заглушка до M6)
    layout/                   # реестр форматов (YAML), подписи отведений, склейка кадров

  layouts/*.yaml              # реестр раскладок: 3x4+rhythm, 6x2, 12x1, single
```

Направление зависимостей: `ecgscan` не импортирует `cardiolens`, кроме
`ecgscan.contract.cardiolens_adapter` (ленивый импорт). `cardiolens` вызывает
`ecgscan` только через адаптер под флагом (`configs/app.yaml: ingestion.photo_backend:
legacy | ecgscan`). Существующий путь пользователя (Telegram-коллектор, `load()`)
по умолчанию не меняется (ТЗ §12).

Переходный период: алгоритмы `cardiolens/layer1_ingestion/{digitize,strip}.py`
переносятся в `ecgscan` по одному, с реэкспортом из старых модулей и
неизменными старыми тестами. Это разрешает противоречие п.1.

## 9. Схема результата

Предложена в [`scan_result.schema.json`](../../src/ecgscan/contract/scan_result.schema.json) (JSON Schema
2020-12) с примером [`scan_result.example.json`](../../src/ecgscan/contract/scan_result.example.json).
Отличия от минимального набора ТЗ §7 (все аддитивные):

- `schema_version` обязателен (ТЗ: «версия схемы обязательна»).
- `warnings[]` рядом с `reject_reasons[]`: `needs_confirmation` объясняется
  кодами (`SPEED_UNCERTAIN`, `GAIN_DEFAULTED`, `LABEL_ORDER_CONFLICT`…).
- `calibration.*_candidates[]`: варианты для экрана подтверждения с уверенностью.
- `calibration.*_source` расширен значением `format_registry`.
  Значения `default` **нет**: если значение не подтверждено ни одним источником,
  поле `null` и статус `needs_confirmation`.
- `leads.*.samples_mv`: элементы `number | null`, где `null` = пропуск. NaN в JSON
  невозможен.
- `leads.*.coverage`, `missing_fraction`, `method`, `box_px`: прослеживаемость.
- `rhythm[]`: длинные полосы отдельно от панелей 12 отведений (на 3×4 «II» есть
  и как панель 2.5 с, и как ритм 10 с).
- `confirmation`: кто (псевдоним), когда, что поправил. Журнал по ТЗ §9.
- `source.header_masked`, `source.client`, `source.client_crop`.

Соответствие `ScanResult` → `SignalRepresentation`:

| ScanResult | SignalRepresentation |
|---|---|
| `leads[L].samples_mv` (мВ, null) | `signal[L]` в мкВ; вне `[start_s, start_s+duration_s)` = 0; внутри null → 0 + `sample_mask` (новое поле) |
| `rhythm[k]` для лида L | заменяет `signal[L]` на всю длину, окно L = вся запись (как `II_rhythm` сейчас) |
| `sampling_rate_hz` | `sampling_rate_hz` |
| — | `source="image"` |
| `status`, `quality.overall` | `provenance.confidence` = `quality.overall`; при `rejected` адаптер **не строит** сигнал (исключение с кодами) |
| `leads[L].quality` | `quality.per_lead_sqi` (предварительно, Слой 2 пересчитает) и новое `provenance.lead_quality` |
| `provenance_flags` | `provenance.digitized=True` + новое `provenance.flags` |
| `calibration`, `layout`, `scan_id`, `pipeline_version` | `provenance.notes` (как сейчас) и новое `provenance.scan` (dict) |
